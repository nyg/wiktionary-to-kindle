# Packaging, CI and release

## Packaging

`scripts/package.sh` runs jlink then jpackage. One bash script covers every platform, since Windows runners provide bash.

- **The JDK module list** was computed with `jdeps --print-module-deps`, plus four modules static analysis cannot see: `jdk.crypto.ec` (without it every HTTPS request fails at handshake), `jdk.localedata` (without it language names degrade to bare uppercase codes), `java.logging` and `jdk.unsupported`. The first two fail *silently*, which is why the script links a probe into the fresh image and runs it there.
- **JavaFX is excluded from the shaded JAR** (`artifactSet` exclude in the shade config). JavaFX resolves to platform-classified native artifacts, so bundling it would tie the CLI JAR to whichever OS built it.
- **The shade config filters `module-info.class`.** atlantafx-base is an explicit module, and its descriptor at the root of the fat JAR would make the JAR claim to be `atlantafx.base`.
- **Only classified JavaFX jars are real modules.** The unclassified ones are ~300-byte stubs that shadow them on the module path, so the script selects by presence of `module-info.class`.
- **Use `$PATH_SEPARATOR`** in module paths and classpaths; Windows uses `;`.
- **The script takes one or more types** (`scripts/package.sh app-image exe`, `scripts/package.sh deb rpm`), defaulting to `detect_default_type` for the host. Collecting the JavaFX modules, linking the runtime image and running the probe happen once; only `jpackage` runs per type. `rm -rf "$OUTPUT_DIR"` therefore lives in `main`, **before** the loop: inside `build_package` it deletes the previous type's output, and a two-type run publishes one file.
- **`platform_arguments` takes the type**, because installer flags are type-specific: `--win-menu --win-dir-chooser --win-per-user-install --win-shortcut` apply to `msi` and `exe` but not to `app-image`, and `--linux-rpm-license-type` only to `rpm`. The Windows `exe` is deliberately per-user (no admin rights, no UAC prompt, as with Scoop) and unsigned, so SmartScreen prompts on first run. Both are documented rather than solved.
- **`--linux-package-name` is pinned to the slug.** jpackage derives it from `--name`, which is `Wiktionary to Kindle`, and deb and rpm names admit neither spaces nor capitals. The pinned value is also the name the uninstall instructions document.
- **jpackage cannot produce a portable single-file `.exe`.** The `exe` type is a WiX-built installer; the app-image is always a directory of launcher, `runtime/` and `app/`, which is what the Scoop ZIP carries. The two Windows assets are alternatives, not duplicates. jpackage 24 and later accept WiX v3, v4 and v5 and pick the newest installed; the runner image ships v3.14 off the `PATH`, so `release.yml` adds it by globbing `C:\Program Files (x86)\WiX Toolset v*\bin`.
- **The script derives the version** by stripping the `wiktionary-to-kindle-` prefix off the built JAR's filename, so that literal must keep matching the pom's artifactId.

## CI

- **`java-ci.yaml`** — `build` runs `mvn verify` under `xvfb-run` on Ubuntu. `package` runs jlink and jpackage on macOS (`dmg`) and Windows (`app-image`). `exe`, `deb` and `rpm` are release-only: a WiX, `fakeroot` or `rpmbuild` breakage surfaces when a release is cut, not in a PR.
- **`screenshots.yml`** — captures the real main window on macOS, Windows and GNOME for the README's `assets/screenshots/`. It runs `ScreenshotLauncher`, a test-sources `main` that opens the window through `App.showMainWindow` with English and Greek already picked and prints `SCREENSHOT READY` once kaikki's language list has arrived. Each OS grabs that one window with its own tooling: `screencapture -l` on macOS, `CopyFromScreen` over the DWM frame bounds on Windows, ImageMagick `import` under Xvfb on Linux. The `compose` job runs `scripts/compose-screenshots.sh`, which gives the Windows and GNOME captures the drop shadow macOS puts on its own (56px either side, 38px above, 74px below), redraws the Windows capture's border and rounds its corners, and lays all three out side by side with captions as `desktops.png`, the one image the README shows. The script targets ImageMagick 6, which is what Ubuntu ships: `convert`/`identify`/`montage`, not `magick`. The workflow runs by hand and on PRs that touch it, the script or the launcher. Nothing commits its output: after a UI change, run it and copy the `screenshots` artifact into `assets/screenshots/`. There is no KDE capture, because KDE keeps KWin's title bar and a bare Xvfb does not draw it.

## Release

`release.yml` is a `workflow_dispatch` with a bump choice. It bumps through `maven-release-plugin` (hence the `-SNAPSHOT` version and the `<scm>` block), builds the DMG, the Windows installer and Scoop ZIP, the deb, the rpm and the portable JAR, publishes, then dispatches to `nyg/homebrew-tap` and pushes a manifest to `nyg/scoop-bucket`. `RELEASE_TOKEN` needs write access to all three repos.

- **The `linux` matrix leg** produces the deb, the rpm **and** the cross-platform JAR, which just needs some runner. It `apt-get install`s `fakeroot` and `rpm` rather than trusting the image inventory.
- **Asset names** are `wiktionary-to-kindle-<version>-<os>-<arch>.<ext>`: `…-macos-arm64.dmg`, `…-windows-x64.exe`, `…-windows-x64-scoop.zip`, `…-linux-x64.deb`, `…-linux-x64.rpm`, and the plain `wiktionary-to-kindle-<version>.jar`. jpackage's own names differ on every platform (`wiktionary-to-kindle_X.Y.Z_amd64.deb`, `Wiktionary to Kindle-X.Y.Z.exe`), so each build step renames by extension glob.
- **Every reference interpolates `VERSION`** from a step-level `env`: the rename steps, the 7z output, `gh release create`, both `sha256sum` inputs and the Scoop manifest url. Only the DMG and the Scoop ZIP are hashed; nothing downstream consumes the others.
- **Renaming an asset** means updating the Homebrew cask in `nyg/homebrew-tap` too, and only **after** a release has published under the new name. The Scoop bucket regenerates itself.
- **The release notes are generated, then appended to.** `git-cliff` writes the changelog, and the `Append install guidance` step adds the Installing section as a heredoc. Filenames in it are written with a literal `VERSION` and rewritten by one `sed` on `wiktionary-to-kindle-VERSION`; a filename that does not start that way needs its own substitution.
